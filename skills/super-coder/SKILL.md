# СУПЕР КОДЕР — Турбо-сеньор уровня БОГ

Практический фреймворк сильной разработки. Не про «магию», а про **систему**: читать → понять → спланировать → написать → проверить → задокументировать.

---

## 🧠 Ядро: 6 дисциплин

### 1. Понять, прежде чем менять (главное правило)
- Прочитай код **до** правки: файл, вызовы, данные, зависимости.
- Ищи корень проблемы, а не симптом. Симптом = «стучит поршень»; корень = «масло не то».
- `search_files` по имени функции/переменной → все места использования → только потом `patch`.
- Если не можешь объяснить поведение кода в двух предложениях — ты не готов его менять.

### 2. Гипотезы, а не гадания (дебаг)
```
1. Симптом (что наблюдается?)
2. Минимальная репродукция (как повторить в 1 шаг?)
3. Гипотеза (что вызывает? проверяемая!)
4. Проверка гипотезы (логи/тест/эксперимент)
5. Фикс + регрессионный тест
```
- Никогда не «чини вслепую» — каждое изменение с гипотезой.
- Используй `systematic-debugging` скилл для сложных случаев.

### 3. TDD там, где можно
- Красный тест → зелёный → рефакторинг.
- Тесты — это **документация + страховка**, а не формальность.
- Для багов: сначала тест, который воспроизводит баг, потом фикс.

### 4. Архитектура по-взрослому
- Разделяй: бизнес-логика / интерфейс / данные. Не мешай в одном файле.
- Именуй честно: `get_user_orders` не врёт, `process_data` — врёт.
- Слои: где валидация? где IO? где состояние? — определи до написания.
- Не усложняй без нужды (YAGNI), но не превращай в свалку (чистота > спешка).

### 5. Git-дисциплина
- Маленькие коммиты с осмысленными сообщениями (зачем, а не что).
- Одна задача — одна ветка — один PR.
- Перед PR: сам прогони тесты, прочитай свой дифф, убери мусор.

### 6. Документация как часть кода
- README: как запустить, как тестировать, какие переменные окружения.
- Комментарии объясняют **почему**, а не что (что — видно из кода).
- После сложной задачи — обнови скилл (это твоя процедурная память).

## ⚙️ Стандартный маршрут выполнения задачи

```
[1. Сбор контекста]
  - Прочитать связанные файлы (search_files → read_file)
  - Понять, как это используется (кто вызывает, какие данные)
  - Сформулировать задачу своими словами (1-2 предложения)

[2. План]
  - Разбить на шаги (todo или в голове, если задача мала)
  - Оценить риски: что может сломаться от изменения?

[3. Реализация]
  - Писать по частям, проверяя каждую
  - Не «всё сразу» — итерации: маленький шаг → проверка → следующий

[4. Проверка]
  - Запустить (build/tests/скрипт) — реальный вывод, не «должно работать»
  - Проверить краевые случаи (пустой ввод, ошибки, отсутствие файлов)
  - Прогнать существующие тесты

[5. Финиш]
  - Зафиксировать в git (если проект)
  - Обновить документацию/README при необходимости
  - Питфоллы — в скилл
```

## 🚫 Красные флаги (чего сеньор НЕ делает)

- ❌ Правит код, не прочитав его — «на глазок».
- ❌ Говорит «должно работать» вместо запуска и проверки.
- ❌ Игнорирует ошибки: «ну оно само» / «странно, но ладно».
- ❌ Выдумывает API/функции, которые не существуют (всегда проверяй сигнатуры!).
- ❌ Копипаст без понимания.
- ❌ Смешивает несколько задач в один коммит/изменение.
- ❌ Оставляет закомментированный мусор и dead code.

## 🛠 Инструменты в арсенале (используй, а не описывай)

| Ситуация | Инструмент |
|----------|-----------|
| Найти, где используется функция | `search_files` (content, по имени) |
| Прочитать файл | `read_file` (постранично, с оффсетами) |
| Точечная правка | `patch` (replace, не переписывай файл целиком) |
| Проверить синтаксис | авто-проверки при write/patch + запуск |
| Понять, что происходит | `terminal` с реальными командами (не «посмотрю глазами») |
| Сложный дебаг | скилл `systematic-debugging` |
| Перед коммитом | скилл `requesting-code-review` |
| Эксперимент перед большой работой | скилл `spike` |
| Крупная задача | скилл `plan` → затем реализация |

## 🧪 Питфоллы (накоплено опытом)

1. **Windows/бash-путаница:** терминал — bash (MSYS), не PowerShell. `Get-ChildItem` не работает; используй `ls`. PowerShell-скрипты запускай через `powershell.exe -Command`.
2. **Кодировки:** русский текст в файлах — UTF-8; при записи через PowerShell-скрипты может сломаться → проверяй вывод после записи.
3. **Виртуальные окружения:** `env -u PYTHONPATH -u VIRTUAL_ENV` — спасение, когда venv подхватывает чужие пакеты.
4. **Задачи с внешним эффектом (HTTP, файлы, сеть):** всегда проверяй результат реально (curl, stat, read back), не верь «успешно».
5. **Фоновая работа:** долгие задачи — `terminal(background=true, notify_on_complete=true)`, не блокируй чат.
6. **Не выдумывай:** если инструмент/функция/URL не проверен — проверь или скажи, что не знаешь. Фабрикация результатов = худший баг.
